Lab results: breaking the code to test the tests

Two modules where a security property broke and the suite stayed green.

The harness is scripts/mutate.py. This round covered the code that had never been mutation-tested: the console and the Cedar PDP.

Why this was needed

verify.ts, dpop.ts, config.ts, the policies, RLS and object storage had all been mutation-tested by hand. The console — the newest code, and where three real bugs had already been found — had not. Hand-editing a file, running a suite and editing it back is slow enough that modules get skipped, and it had produced two recorded harness failures: one that grepped for counts that never matched and therefore measured nothing, and one where a cp restore silently failed and left the source mutated.

scripts/mutate.py is built so those cannot recur:

  • Exit code, never output parsing.
  • The restore is verified by checksum; a failed restore aborts the run.
  • A mutation that does not apply is a FAILURE — “the suite stayed green” and “the code never changed” are otherwise indistinguishable.
  • A green control is required first, or no result below means anything.

Negative-tested: a spec whose text is not in the file exits 1 and reports did-not-apply.

1. console/session.ts — two real gaps, both closed

First run: 0 of 3 caught.

Mutation First run After
expired sessions are ACCEPTED survived caught
CSRF comparison ALWAYS MATCHES survived caught
CSRF length pre-check removed survived survived (correct)

The CSRF gap was the serious one. The suite had tests named “sign-out without a CSRF token does NOT end the session” and “creating WITHOUT a valid CSRF token is refused”. Both send csrf=wrong — five characters, against a 43-character token. So they were rejected by the cheap length pre-check and never reached the constant-time comparison.

Deleting the constant-time comparison left the whole suite green. The property — “a well-formed but wrong token is refused” — genuinely broke, and nothing noticed. This is the opposite of the documented server.ts case, where a survivor was fine because another layer kept the property intact.

Fixed: two tests added. One sends a token of the correct length with one character changed, so only the comparison can refuse it. The other tests expiry directly on the store.

Token length 43 · tests sending the 5-char "wrong": 2 · tests sending a same-length wrong token: 0 → 1.

2. console/oidc.ts — a module with NO test coverage at all

First run: 0 of 4 caught. Every single one survived.

The four included “the ID-token nonce check always passes” — the defence against token substitution. It survived because the console tests inject a stub ConsoleOidc. The real OidcClient — 232 lines: nonce check, discovery, code exchange, logout URL — was never instantiated by any test.

That is the most dangerous shape a coverage gap can take: the route tests look like they cover sign-in, and the one component that decides whether a token belongs to this flow was never run.

Fixed: apps/api/test/oidc.test.ts, 13 tests. The nonce suite alone has seven cases — accepts the right nonce; refuses a different one; refuses none; refuses a non-string; refuses a missing token; refuses five kinds of malformed token without throwing; and refuses an empty expected nonce against a non-matching token. Plus buildAuthorizationUrl carrying state and nonce and not leaking the client secret into a browser-visible URL, and live-provider checks for discovery, logout and a refused exchange.

Re-run: 4 of 4 caught.

3. pdp-cedar.ts — 3 of 4 caught, and the survivor is correct

Mutation Result
an allow alongside evaluation ERRORS is honoured caught
a FAILED evaluation grants access survived
an UNREPRESENTABLE request grants access caught
EVERY decision becomes Allow caught

The survivor is not a blind spot, and that was checked rather than assumed. Probed against the real Cedar wasm:

missing attr path   type=success  decision=deny  errors=1     ← the errors path, caught
type mismatch       type=success  decision=deny  errors=1     ← same
no permit           type=success  decision=deny  errors=0

isAuthorized does not return non-success for realistic input — it returns success with the failure in diagnostics.errors, which the first mutation proves is guarded. The non-success branch guards wasm failure or corruption: fail-closed defence in depth, unreachable through input.

What this round says about the suites

Two modules out of three had mutations that survived while a real security property was broken. Neither was a broken test — both were tests that stopped short of the interesting case:

  • the CSRF tests stopped at the length check
  • the console tests stopped at the stub boundary

A suite can be green, thorough-looking, and still never execute the line that matters. The only way to know is to break the line and watch.

Next round

jwks.ts (cache and rotation) and the object-storage adapters have no recorded mutation results. server.ts and policies have documented survivors that are already explained.

Round 2 — jwks.ts and the object-storage adapters

4. jwks.ts — no tests existed, and the DoS bound was unasserted

60 lines wrapping jose’s remote key set. Most of it is the library’s job, so re-testing jose would be noise. But two settings in it are ours, and both are security-relevant:

Setting Default What it bounds
cooldownDuration 30s how often an unknown kid can force a refetch
cacheMaxAge 600s how stale the key set may be before rotation is seen

If the cooldown were 0, every unauthenticated request carrying an invented kid would trigger an outbound fetch to the identity provider — the one service that must stay up for anyone to log in. Nothing tested that it was bounded.

apps/api/test/jwks.test.ts now does, with a counting HTTP server:

Mutation Result
the cooldown is DISABLED caught
the key cache is DISABLED caught

The control matters as much as the test. A test asserting “few fetches” passes trivially if nothing is ever fetched, so the suite also asserts that with cooldownDurationSec: 0 the same burst does produce repeated fetches. If that control ever stops firing, the bounded test above has stopped measuring anything.

5. Object storage — three layered defences, and what a surviving mutant means

Mutation Result
filesystem: tenant id not encoded caught
filesystem: the ref allowlist accepts .. and slashes survived
filesystem: the resolved path is not checked for containment survived
filesystem: the artifact id used raw caught (after a test was added)
s3: the tenant id is not encoded caught
s3: the artifact id used raw survived (correct — see below)

The two path survivors are the layered defences, and the double is caught

Defences 2 and 3 are deliberately redundant. Each alone survives because the other still holds, which is the point of layering. The question that matters is whether removing BOTH goes red — and it does:

DEFENCES 2 AND 3 removed together -> 1/1 caught

So the survivors are correct rather than blind. This is the same shape as the server.ts result: a surviving mutant is not automatically a gap.

The artifact-id gap was real, and was found by mutating

Nothing asserted on the ref that put() returns — and the ref is what every later read is built from. Removing the sanitising left the whole suite green. A test now feeds six hostile ids (../../other-tenant/secret, .., a/b/c, with space, a Windows traversal, and a normal one) and asserts the ref is one path segment.

It belongs to the path-based adapters only. The in-memory store keys a Map, so its ref is tenant/id-uuid and a separator there is meaningful rather than dangerous. Writing the test in the shared contract first made it fail for in-memory — which is how that distinction surfaced.

The S3 survivor is correct, and that was measured rather than assumed

S3 has no filesystem, so .. in a key is a character. Probed directly:

PUT  tenants/acme/../../other-tenant/secret  -> 200
GET  tenants/acme/../../other-tenant/secret  -> 'ESCAPED'
GET  tenants/other-tenant/secret             -> 404

The key is stored literally; nothing escapes the prefix. So removing safeId does not break tenant isolation on this store. The sanitising is defence in depth aimed at S3-compatible implementations that do normalise .. — and this evidence says s3mock is not one of them. Recorded as a known unasserted defence rather than a closed gap.

What round 2 says

The harness earned its place twice in this round:

  • It refused to report 5 mutations as “survived” when my find strings did not match — they had 6-space indentation and the code has 4. Exit-code reporting made that a loud failure instead of a quiet “the suite is fine”.
  • It refused to run at all when the control went red, which is what caught a test I had written too strictly (!ref.includes("..") rejects a harmless literal .. inside an opaque segment).

Round 3 — the modules that still had no mutation results

Inventory first: every apps/api/src/**/*.ts against every spec in lab/mutation/. Three modules had tests but had never been mutated.

6. ports/replay-cache.ts — 4 of 4 caught

The DPoP single-use enforcement: 66 lines, and the whole of “a jti may be used once”.

Mutation Result
a REPLAY is accepted caught
the jti is remembered with an expiry of NOW caught
every request is refused (fail-closed but useless) caught
the sweep never evicts (memory, not correctness) caught

The second one is the interesting case: the entry is stored, so a naive “is it remembered” test would pass, but it is forgotten on the very next sweep. Something tests the interval, not just the insertion.

7. console/routes.ts — 3 of 3 caught

544 lines, and the first time any of it was mutated.

Mutation Result
LOGOUT loses its CSRF check caught
EVIDENCE CREATION loses its CSRF check caught
requireSession treats a missing session as valid caught

8. ports/memory-repository.ts — 2 of 3, survivor correct

Mutation Result
findById searches EVERY tenant’s bucket caught
list returns EVERY tenant’s records caught
a CROSS-TENANT WRITE is accepted survived (correct)

Checked rather than assumed. The guard refuses a record whose tenantId differs from the scope it is written under. Following the write path in server.ts:

  • the scope is { tenantId: auth.tenantId } (from the verified token)
  • the record is written as { tenantId: tenant.tenantId, ... } — the same object

So the two can never differ, and the guard cannot fire through the API. The handler’s own comment states the reason: “there is no request parameter that names one, so a caller cannot create a record in someone else’s tenant because there is nothing to point at.”

This is the third instance of the same shape (server.ts, pdp-cedar.ts, and now this): a surviving mutant whose property still holds because the state it guards cannot be constructed. The discipline that separates it from a real gap is following the data to the call site, not reading the guard in isolation.

Coverage after three rounds

Every module with decision logic now has a mutation result. The exceptions are the ones with nothing to mutate: errors.ts (constructors), index.ts (wiring), and the ports/*.ts interfaces.
